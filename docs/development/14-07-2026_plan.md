# Staged Delivery: Free-Text Metadata Extraction

A **delivery-ordered** view of the free-text work. The component-ordered plan in
[plan_free_text.md](plan_free_text.md) is the source of truth for *what* each piece is and *what is
already done*; this document reorders the remaining work into shippable stages,
each demonstrable on its own rather than back-loaded into a single big-bang
release.

Status legend: ✅ done · 🟡 partial · 🔲 not started.

## Why free-text is the right thing to ship first

Free-text metadata extraction is **study-scale**: one record per document or
corpus, cardinality 1, every field readable from prose. In the terms of the
[analysis log](14-07-2026_analysis.log.md), it sits entirely inside the layer *a
model may write directly*. It needs **none** of the executor reshape (no change to
`Task.player`, no deterministic transform steps, no mapping artifact). That makes
it the lowest-risk, most self-contained deliverable available, and it can proceed
independent of the two open decisions (schema, and deposit count) that gate the
ShareTrait data-model work.

It also **double-counts**. The two heaviest stages here — the text toolset and the
PDF reader — are exactly Phase 1 of the ShareTrait reshape's Milestone 1 (the probe
found PDFs supplied 42 of 139 filled attributes against the CSVs' 9). Shipping
free-text extraction *is* the front half of the deposit work, delivered as its own
product.

## Foundation already in place ✅

Done and verified (see [plan_free_text.md](plan_free_text.md) for detail and the
[change log](09-07-2026_change.log.md)):

- **Context + tool refactors.** Capability split (base `ExecutionContext` +
  `TabularContext` + `TextContext`); typed `ResourceInfo`; resource-level
  relationships; `is_multi_resource`. Tools gate on `isinstance(ctx, requires)`;
  roles request toolset globs; dispatch derived from each tool's signature.
- **`TextContext`** (`context/text_context.py`) — `read_text`, `iter_chunks` /
  `get_chunks`, `search`, `TextResourceInfo`. Pluggable chunker.
- **Wiring** — `.txt`/`.md`/`.markdown`/`.rst` → `ContextType.TEXT`; classifier and
  factory dispatch text for path / list / dict / directory.
- **Tool gating for players** — a player is never constructed holding a tool the
  context cannot serve; plan validation passes on text contexts.

**Net state today:** a text context runs end-to-end, but sees only the six
`universal` tools, has no document-specialist role, and has no document-oriented
standard to target. It executes; it does not yet extract *well*, and nothing
measures how well.

## Delivery principle

[plan_free_text.md](plan_free_text.md) orders by component: all tools (Phase 3), then players (Phase 4),
then the standard (Phase 5), then tests (Phase 6). Nothing ships until Phase 5. This
plan instead ships the thinnest working extractor first and **thickens it**, so each
stage is independently demoable on a real document.

**Measurement is deferred, by decision.** A golden-record auditor — automated
scoring of coverage and confabulation — is the right eventual discipline (and is
proven out on the ShareTrait record), but it is apparatus ahead of the thing it
measures while the text pipeline can barely run. Until it exists, each stage's
acceptance is a **human read of the output on a sample document**, not a number.
The one criterion to hold by eye at every stage: **no field asserted that the
document does not support** — a convincing but unsupported value is a regression,
not progress. Revisit the auditor once Stage 2 output is worth scoring; see
[how it would be built](#deferred-the-auditor).

## Stage 1 — walking skeleton 🔲 *(the baseline)*

The thinnest end-to-end path, using the pipeline **exactly as it stands** — the six
universal tools plus `metadata_generator`. No new tools, no new role.

- A minimal `document_general` standard in `STANDARD_DEFINITIONS` — just `title`,
  `description`, `subject`, `language`, `keywords`. (Phase 5, trimmed.)
- Run it on a real document (start with the deposit's `DatasetContent.txt`, or a
  public dataset README).

It will be mediocre — the agent can only sample and preview, not investigate. **That
is the point.** This stage proves the whole path integrates and gives a concrete
reference output every later stage is compared against by eye.

**Ships:** "descriptive metadata from a text file." **Acceptance:** a valid
`document_general` record on the sample document, read by a human and judged
plausible, with **no unsupported field** invented.

## Stage 2 — make the agent investigate 🔲 *(the first quality stage)*

Give the agent the ability to *read* the document rather than glance at it.

- **Text toolset** — `src/tools/text/`, `requires=TextContext`, registered under
  `text.*`: `get_sample_passages`, `search_text`, `get_document_stats`,
  `detect_language`. (Phase 3, minus the spatial/temporal extractors — those are
  Stage 3.) Additive, no gating-table edits.
- **`text_analyst` role** (or text prompts for `data_analyst`) equipped with the
  toolset; mention the text tools in the planner prompt. (Phase 4's remaining half.)

**Ships:** noticeably better extraction on the same document. **Acceptance:** the
record is visibly richer and better-grounded than the Stage 1 reference output when
the two are read side by side, still with no unsupported field. This is the first
stage whose value is a delta, not a feature — and the first output worth building
the auditor for.

## Stage 3 — breadth 🔲

Widen from one prose field-set to richer records and multi-file corpora.

- Content-derived `extract_temporal_mentions` / `extract_spatial_mentions` feeding
  the existing `spatial_temporal_specialist` — dates and places found *in the text*,
  populating `temporal_coverage` / `spatial_coverage` (textual). (Rest of Phase 3.)
- Multi-document corpora and cross-document relationships (shared entities,
  citations) via an overridden `TextContext._discover_relationships()`; the
  `RelationshipInfo` groundwork already exists. (Phase 5's relationship half.)
- Round out `document_general`: `document_type`, `authors`.

**Ships:** richer records, multi-file support. **Acceptance:** temporal/spatial and
multi-doc sample inputs produce sensible records without degrading the single-doc
output from Stage 2.

## Stage 4 — PDF 🔲 *(the bridge to the deposit work)*

The highest-leverage modality, and the point where this delivery starts paying into
the ShareTrait reshape.

- A PDF reader producing text resources (no PDF dependency exists in the project
  today). `.pdf` → registry mapping; factory dispatch.
- The entire Stage 2–3 toolset and role apply unchanged — PDF is just another text
  resource.

**Ships:** "we can read PDFs." **Acceptance:** the deposit's `Materials and
Methods.pdf` yields a `document_general` record; this is literally Milestone 1 Phase
1 of [the reshape](14-07-2026_analysis.log.md).

## Build-order ↔ ship-order

The [plan_free_text.md](plan_free_text.md) phases map onto these stages so the two views cannot drift:

| Stage | plan.md phases consumed | Executor reshape needed? |
|---|---|---|
| 1 walking skeleton | Phase 5 (minimal `document_general`) | no |
| 2 investigate | Phase 3 (core tools), Phase 4 (`text_analyst`) | no |
| 3 breadth | Phase 3 (mention extractors), Phase 5 (relationships) | no |
| 4 PDF | *(new; = reshape Milestone 1 Phase 1)* | no |
| throughout | Phase 6 (tests/example/docs, per stage) | no |

**No stage touches the executor.** That is the whole strategic reason free-text
ships cleanly.

## One decision that reorders the stages

Who is the deliverable *for*?

- **Generic descriptive metadata** (Dublin-Core-shaped documents) → the order above
  is right; `document_general` is the target.
- **Text as the on-ramp to the ShareTrait deposit** → pull **Stage 4 (PDF) ahead of
  Stage 2**, because the metadata you actually need lives in the PDFs, and the
  general prose toolset would otherwise sit ahead of higher-value work.

Default: the first, unless the real customer is the deposit.

## Friction points and notes

Carried from [plan_free_text.md](plan_free_text.md), still live:

- **Capability discovery is implicit.** Consumers ask `isinstance(ctx,
  TabularContext)`. Fine for two modalities; when PDF arrives as text-plus-images,
  prefer an explicit `capabilities` set over a deeper inheritance tree.
- **`.txt` is not always prose.** A `.txt` may be delimited data; the classifier may
  eventually want a content sniff rather than trusting the extension.
- **`ContextType` is a closed enum.** Adding `PDF` is a one-line edit plus a registry
  mapping; acceptable, not a base-class concern.
- **Two loose ends from the tool refactor.** The investigate phase has only been
  exercised against a scripted LLM, never a live provider; and roles now see a
  slightly wider tool set than their old hand-listed one — intentional, but the
  output-quality impact is unmeasured. Stage 1 is the first live-provider run, which
  closes the first; the second stays open until the auditor lands (below).

## Deferred: the auditor

Skipped for now — measurement apparatus ahead of a pipeline that can barely run on
text. Parked here so it is a decision, not an omission, and can be picked up once
Stage 2 output is worth scoring.

It is deterministic code (no LLM) that sits **outside** the pipeline — it imports
`run_metadata_extraction`, never the reverse — and scores a run against a hand-built
golden record on three axes, in priority order: **confabulation** (fields filled
with no support in the source; the golden record marks which fields are
unsourceable, and any non-null value there is a flag), **conformance** (validates
against the standard), then **coverage** (fields correctly filled). Coverage ranks
last on purpose: optimizing it first teaches the system to invent. Home: a small
`eval/` package with fixtures, a pure `audit()` function, and a runner; later a
pytest that gates on zero confabulation. Until then, every stage's acceptance above
is a human read, and the confabulation criterion is enforced by eye.
